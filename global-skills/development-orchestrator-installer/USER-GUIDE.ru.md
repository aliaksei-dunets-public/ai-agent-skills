# Руководство пользователя: Development Orchestrator и Installer

## 1. Назначение

В комплект входят два связанных навыка:

- **`development-orchestrator-installer`** — анализирует проект, находит существующие инструкции, навыки, документацию, task-management и команды качества, после чего устанавливает или обновляет оркестратор с учётом контекста проекта.
- **`development-orchestrator`** — выполняет конкретную задачу разработки по обязательному жизненному циклу, вызывает дочерние навыки и управляет статусами задачи.

Рекомендуемый принцип использования:

```text
Installer отвечает за настройку системы.
Orchestrator отвечает за выполнение задач.
Дочерние навыки отвечают только за свою специализированную работу.
```

Не следует использовать Installer для реализации функциональности, а Orchestrator — для самостоятельной перестройки собственной архитектуры.

---

## 2. Стандартный жизненный цикл задачи

Версия `development-orchestrator` 1.2.0 использует следующую схему:

```text
created
  ↓
in_progress
  ↓
базовые тесты и project tools
  ↓
task-review через отдельного субагента
  ↓
code-review через другого субагента
  ↓
review
  ↓
явное подтверждение пользователя
  ↓
approved
  ↓
создание и запуск тестов
  ↓
проверка покрытия
  ↓
post-test project tools
  ↓
doc-sync
  ↓
memory sync
  ↓
архивирование
  ↓
done
```

Основные статусы задачи:

| Статус | Значение |
|---|---|
| `created` | Задача создана и ещё не взята в работу |
| `in_progress` | Агент выполняет план или исправляет замечания |
| `review` | Реализация прошла `task-review` и `code-review`, ожидается решение пользователя |
| `approved` | Пользователь подтвердил реализацию; выполняются тесты и документация |
| `done` | Все обязательные стадии завершены, задача перенесена в архив |

Для технического состояния используется отдельное поле:

```text
ready | running | waiting_approval | blocked
```

`Status` отражает бизнес-этап задачи, а `Execution state` — текущее состояние выполнения.

## 3. Когда использовать Installer

Используйте `development-orchestrator-installer` в следующих случаях:

- оркестратор впервые добавляется в репозиторий;
- проект уже содержит навыки, но их нужно сопоставить с ролями оркестратора;
- изменились структура проекта, test pipeline, документация или task-management;
- обновилась версия `development-orchestrator`;
- часть установки была удалена или повреждена;
- необходимо проверить совместимость проекта без изменения файлов.

Installer поддерживает четыре режима:

| Режим | Назначение |
|---|---|
| `audit` | Только анализ, без изменения проекта |
| `install` | Первичная установка |
| `upgrade` | Обновление установленной версии с сохранением настроек |
| `repair` | Восстановление неполной или повреждённой установки |

### Рекомендуемый первый запуск

```text
Используй development-orchestrator-installer в режиме audit.
Проанализируй проект, существующие навыки, инструкции, документацию,
task-management, тесты, coverage и CI. Не изменяй файлы.
Подготовь capability matrix, список конфликтов и installation plan.
```

После проверки отчёта:

```text
Используй development-orchestrator-installer в режиме install.
Примени подготовленный installation plan. Создай backup затрагиваемых
файлов, установи orchestrator, настрой adapters, выполни validation и dry run.
Не изменяй production-код.
```

### Что должен проверить пользователь после установки

Установка не должна считаться полностью готовой, пока не подтверждены:

- путь к активным задачам;
- путь к архиву завершённых задач;
- путь к `memory.md`;
- сопоставление всех пяти обязательных ролей;
- механизм запуска независимых субагентов для `task-review` и `code-review`;
- свежий контекст и read-only режим review-субагентов;
- inventory дополнительных project tools и их hook mapping;
- реальные команды сборки, проверок и тестирования;
- команда измерения покрытия;
- официальные источники документации;
- успешный structural и contract validation;
- успешный либо обоснованно `static-only` dry run.

Статус `installed_but_blocked` означает, что файлы могли быть установлены, но полный цикл пока нельзя безопасно запускать.

## 4. Когда использовать Development Orchestrator

Используйте `development-orchestrator`, когда задача должна быть выполнена полностью — от выбора до архивирования.

### Запуск конкретной задачи

```text
Используй development-orchestrator и выполни TASK-0123 по полному циклу.
Следуй конфигурации проекта. Остановись после перехода в review и запроси
моё явное подтверждение перед тестированием.
```

### Автоматический выбор следующей задачи

```text
Используй development-orchestrator. Выбери следующую доступную задачу
со статусом created согласно orchestrator.config.yaml и выполни её
по обязательному процессу.
```

### Продолжение прерванной задачи

```text
Продолжи TASK-0123 через development-orchestrator с текущего сохранённого
этапа. Сначала проверь task-файл, review history, approval, результаты тестов
и work log. Не повторяй уже успешно завершённые стадии без причины.
```

### Ревью через субагентов

Канонический оркестратор всегда использует `review_execution.mode:
subagent_required`. Исключений для self-review основным агентом или в текущем
чате нет. Каждый запуск `task-review` и `code-review` обязан выполняться
отдельным субагентом со свежим контекстом и без права записи.

Обязателен следующий процесс:

```text
Основной агент выполняет задачу
→ новый task-review субагент проверяет план и acceptance criteria
→ основной агент исправляет замечания
→ при необходимости новый task-review субагент выполняет второй запуск
→ новый code-review субагент проверяет код
→ основной агент исправляет замечания
→ при необходимости новый code-review субагент выполняет второй запуск
```

Требования к изолированным субагентам:
- каждый запуск review получает свежий изолированный контекст;
- `task-review` и `code-review` используют разных субагентов;
- review-субагенты по умолчанию не имеют права записи;
- review-субагенты не меняют статусы и не исправляют код;
- каждый вид review допускает максимум два запуска на ревизию.

### Автоматическая синхронизация задач

Метаданные задач хранятся в формате YAML frontmatter внутри файлов `TASK-XXXX.md`. При каждом изменении статуса задачи Оркестратор запускает `python .ai/scripts/sync_tasks.py` для автоматической перегенерации индексных файлов `tasks.md`.

Если платформа не поддерживает обязательных субагентов, полный цикл получает
статус `installed_but_blocked` или задача — `blocked`. Нельзя незаметно
заменять субагента основным агентом.

### Подтверждение реализации

На этапе `review` пользователь должен дать однозначное подтверждение:

```text
approve TASK-0123
```

или:

```text
Подтверждаю изменения по TASK-0123. Продолжай тестирование,
синхронизацию документации и завершение задачи.
```

Сообщения вроде «хорошо», «понятно», «посмотрю позже» не должны автоматически считаться approval.

### Запрос исправлений вместо approval

```text
Не подтверждаю TASK-0123. Исправь обработку ошибки при пустом ответе API,
обнови план и создай новую ревизию задачи.
```

В этом случае задача возвращается в `in_progress`, номер ревизии увеличивается, а review-счётчики новой ревизии начинаются заново.

## 5. Использование дочерних навыков отдельно

Обязательные дочерние роли:

- `task-manager`;
- `task-review`;
- `code-review`;
- `create-test`;
- `doc-sync`.

Каждый навык можно запускать отдельно. Это полезно для локальной проверки, диагностики или разовой операции.

Пример отдельного запуска:

```text
Запусти code-review только для изменений TASK-0123.
Не меняй статус задачи и не продолжай полный lifecycle.
Верни структурированный результат с severity, location и required_action.
```

Отдельный запуск дочернего навыка **не означает**, что соответствующая стадия полного цикла автоматически считается пройденной. Для зачёта результата оркестратор должен:

1. связать результат с конкретной задачей и ревизией;
2. проверить формат результата;
3. записать его в task history;
4. убедиться, что проверялась актуальная версия изменений.

Дочерние навыки не должны самостоятельно:

- переводить задачу между основными статусами;
- объявлять полный цикл завершённым;
- обходить approval;
- архивировать задачу вне команды оркестратора.

---


### Обязательный запуск review через субагентов

В полном цикле `task-review` и `code-review` не выполняются основным агентом, который писал код.

Правильная схема:

```text
Основной агент реализует задачу
→ новый task-review субагент проверяет план и acceptance criteria
→ основной агент исправляет замечания
→ при необходимости новый task-review субагент выполняет второй запуск
→ новый code-review субагент проверяет код
→ основной агент исправляет замечания
→ при необходимости новый code-review субагент выполняет второй запуск
```

Требования:

- каждый review-run получает свежий изолированный контекст;
- `task-review` и `code-review` используют разных субагентов;
- review-субагенты по умолчанию не имеют права записи;
- review-субагенты не меняют статусы и не исправляют код;
- основной агент не может засчитать собственную самопроверку как обязательный review;
- максимум два запуска каждого review на одну ревизию задачи.

Если платформа не поддерживает субагентов, полный цикл получает статус `installed_but_blocked` или задача — `blocked`. Нельзя незаметно заменить субагента основным агентом.

Для отдельного review используйте формулировку:

```text
Запусти отдельного code-review субагента со свежим контекстом для TASK-0123.
Предоставь ему задачу, acceptance criteria, diff и проектные правила.
Запрети изменение файлов и task status. Верни структурированный review-result.
```

## 6. Настройка проекта

Основная конфигурация хранится в:

```text
.ai/orchestrator.config.yaml
```

Проектный индекс контекста рекомендуется хранить в:

```text
.ai/orchestrator.project.md
```

### Что обычно можно менять через конфигурацию

| Область | Примеры |
|---|---|
| Пути | task-файл, архив, `memory.md`, project context |
| Интеграции | имена и пути навыков, native/adapter mapping |
| Review execution | subagent launcher, reviewer profiles, isolation и write access |
| Project tools | diagnostics, health checks и другие hooks с точкой запуска и failure policy |
| Проект | языки, framework, source/test/docs roots |
| Команды | build, lint, typecheck, test, coverage, docs check |
| Выбор задач | приоритет, зависимости, стратегия выбора |
| Архив | удалять ли задачу из активного файла, сохранять ли полную историю |
| Контекст | всегда загружаемые и загружаемые по требованию документы |
| Качество | coverage threshold и scope, если это не ослабляет обязательную политику проекта |

После ручного изменения конфигурации следует запустить:

```text
Используй development-orchestrator-installer в режиме repair.
Проверь изменённый orchestrator.config.yaml, ссылки, skill mapping,
контракты и dry run. Не перезаписывай корректные ручные настройки.
```

### Подключение диагностики, health check и других инструментов

Да, Installer должен обнаруживать дополнительные инструменты проекта и предлагать их интеграцию в Orchestrator. Однако они подключаются только после классификации.

Поддерживаемые варианты:

| Решение | Когда применяется |
|---|---|
| `integrate-required` | Безопасная обязательная проверка; ошибка блокирует lifecycle |
| `integrate-optional` | Полезная проверка; ошибка фиксируется как warning |
| `on-demand` | Диагностика запускается только при проблеме или явном запросе |
| `manual-only` | Нужны credentials, внешний сервис или действие пользователя |
| `excluded` | Инструмент destructive, выполняет deployment или меняет production data |
| `unresolved` | Недостаточно информации для безопасного подключения |

Допустимые точки запуска:

- `on_demand` — во время реализации для диагностики;
- `post_implementation` — сразу после изменения кода;
- `pre_review` — обязательный gate перед review-субагентами;
- `post_tests` — после основного test pipeline;
- `pre_done` — последний проектный gate перед завершением.

Пример:

```yaml
project_tools:
  - id: "project-health-check"
    type: "command"
    ref: "scripts/health-check.sh"
    stage: "pre_review"
    required: true
    safe_to_run: true
    failure_policy: "block"
    conditions: []
```

Installer не должен автоматически включать инструмент только потому, что нашёл файл с похожим именем. Он обязан подтвердить entrypoint, безопасность, стадию и failure policy.

После добавления нового инструмента в проект запустите:

```text
Используй development-orchestrator-installer в режиме upgrade.
Повторно выполни audit project tools, найди новые diagnostics и health checks,
предложи hook mapping, обнови config и dry run. Не запускай destructive,
deployment или production-data инструменты.
```

### Что не следует помещать в конфигурацию

Не храните в `orchestrator.config.yaml`:

- длинные coding standards;
- полную архитектурную документацию;
- большие API-спецификации;
- секреты и токены;
- детальные инструкции дочерних навыков;
- временный прогресс конкретной задачи.

Конфигурация должна ссылаться на канонические документы, а не дублировать их.

## 7. Как правильно изменить процесс разработки

### 7.1. Сначала классифицируйте изменение

Изменения делятся на три уровня.

#### Уровень A — параметрическая настройка

Процесс остаётся тем же, меняются только параметры:

- пути;
- команды;
- source/test/docs roots;
- skill mapping;
- task selection;
- coverage threshold;
- число попыток исправления тестов;
- архивирование;
- context loading.

Такие изменения выполняются через `orchestrator.config.yaml`, затем проверяются режимом `repair`.

#### Уровень B — проектная адаптация

Жизненный цикл сохраняется, но проекту нужны дополнительные действия:

- security scan;
- database migration check;
- performance benchmark;
- SAP activation/check;
- mobile build;
- отдельная архитектурная проверка;
- несколько test runners;
- внешний issue tracker.

Правильный способ:

1. создать или подключить специализированный навык, command или MCP tool;
2. классифицировать его как required, optional, on-demand, manual-only или excluded;
3. определить hook stage и failure policy;
4. добавить `project_tools` mapping или тонкий adapter;
5. сохранить общую state machine;
6. обновить project context и installation report;
7. выполнить `repair` или `upgrade` и dry run.

Например, безопасный health check можно подключить как обязательный `pre_review` gate, а тяжёлую диагностику — как `on_demand`, не создавая новый бизнес-статус.

#### Уровень C — изменение жизненного цикла

К этому уровню относятся:

- изменение порядка стадий;
- добавление или удаление обязательного approval gate;
- перенос тестирования до пользовательского approval;
- новые основные статусы;
- удаление `task-review` или `code-review`;
- изменение правила двух review;
- отказ от независимых review-субагентов;
- разрешение автоматического approval;
- изменение условий `done`;
- другая модель архивирования.

Это **не обычная настройка**. В версии 1.2.0 такие правила являются защищёнными инвариантами.

Изменение lifecycle должно оформляться как новая версия процесса.

### 7.2. Процедура изменения lifecycle

#### Шаг 1 — Создать Process Change Proposal

Используйте шаблон:

```markdown
# Process Change Proposal: PCP-XXXX

## Причина изменения

Почему текущий процесс не подходит проекту.

## Текущий процесс

Текущая последовательность стадий и статусов.

## Предлагаемый процесс

Новая последовательность стадий и статусов.

## Scope

Проектный процесс или новая общая версия навыка.

## Изменения state machine

- добавленные статусы;
- удалённые статусы;
- новые переходы;
- запрещённые переходы.

## Gates

Для каждой стадии:

- условие входа;
- обязательные действия;
- условие успешного завершения;
- поведение при ошибке;
- лимиты повторов;
- требуемые артефакты.

## Active task migration

Как обрабатываются уже созданные и выполняемые задачи.

## Compatibility

Какие skills, adapters, task formats и platform instructions изменяются.

## Validation

Какие сценарии должен проверить dry run.

## Rollback

Как вернуть предыдущую версию процесса.

## Approval

Кто одобрил изменение процесса и когда.
```

#### Шаг 2 — Определить область изменения

- **Только один проект:** создайте project-specific версию или профиль процесса и явно зафиксируйте отклонение.
- **Все проекты:** обновите канонический `development-orchestrator` и Installer asset.

Не изменяйте только установленную копию оркестратора, если изменение должно переноситься на другие проекты. Иначе следующая установка или upgrade перезапишет локальную правку.

#### Шаг 3 — Назначить новую версию

Рекомендуемое версионирование:

| Изменение | Версия |
|---|---|
| Исправление текста без изменения поведения | Patch: `1.1.0 → 1.1.1` |
| Новый необязательный совместимый hook или capability | Minor: `1.1.0 → 1.2.0` |
| Статусы, порядок стадий, approval, обязательные gates | Major: `1.x → 2.0.0` |

#### Шаг 4 — Обновить все связанные контракты

При изменении lifecycle необходимо синхронно проверить и обновить:

- canonical `development-orchestrator/SKILL.md`;
- копию в `installer/assets/`;
- Installer invariants и contract validation;
- `orchestrator.config.yaml` template;
- task schema и шаблон задачи;
- adapters;
- state transition rules;
- installation manifest format, если требуется;
- user guide;
- dry-run scenarios;
- migration rules для активных задач.

#### Шаг 5 — Не менять активную задачу молча

Для задач в `in_progress`, `review` или `approved` выберите один вариант:

1. завершить задачу по старой версии процесса;
2. явно мигрировать её на новую версию;
3. вернуть задачу в безопасное состояние и создать новую ревизию.

В task-файле рекомендуется фиксировать:

```text
Process version: 1.1.0
```

После миграции:

```text
Process version: 2.0.0
Migration: PCP-XXXX
```

#### Шаг 6 — Выполнить audit и upgrade

```text
Используй development-orchestrator-installer в режиме audit.
Проверь Process Change Proposal PCP-XXXX, новую версию orchestrator,
обновлённые contracts, task schema, adapters и migration rules.
Не изменяй проект.
```

После принятия отчёта:

```text
Используй development-orchestrator-installer в режиме upgrade.
Примени процесс версии 2.0.0 согласно PCP-XXXX. Создай backup,
мигрируй только согласованные файлы, выполни structural validation,
contract validation и dry run для всех новых переходов.
```

#### Шаг 7 — Проверить сценарии dry run

Минимально проверь:

- нормальное прохождение полного процесса;
- замечания первого review и успешный повтор;
- замечания второго review и блокировку;
- запрос изменений пользователем;
- approval;
- failed tests;
- недостижимое coverage;
- `not_applicable` test type;
- ошибка `doc-sync`;
- восстановление после прерванной сессии;
- архивирование;
- миграцию активной задачи со старой версии.

### 7.3. Что нельзя делать при изменении процесса

Не следует:

- добавлять противоречащую инструкцию только в `AGENTS.md` или `CLAUDE.md`;
- вручную менять статусы без изменения state transition rules;
- обходить review через отдельный запуск навыка;
- использовать новую ревизию для обхода лимита review;
- менять установленный `SKILL.md`, не обновляя canonical source Installer;
- понижать quality gate без явного решения владельца процесса;
- смешивать изменение lifecycle с реализацией продуктовой задачи;
- мигрировать активные задачи без записи версии процесса;
- объявлять upgrade успешным без dry run и rollback plan.

## 8. Настройка дочерних навыков

Installer должен сопоставить существующие навыки с пятью обязательными ролями.

### Native integration

Используется, когда существующий навык уже:

- выполняет нужную ответственность;
- принимает достаточный контекст;
- возвращает структурированный результат;
- не управляет чужими стадиями lifecycle;
- не конфликтует с политикой оркестратора.

### Adapter integration

Adapter нужен, если существующий навык полезен, но:

- называется иначе;
- имеет другой формат входа или выхода;
- возвращает свободный текст;
- совмещает несколько ролей;
- самостоятельно меняет task status;
- использует несовместимые severity или status values.

Adapter должен преобразовывать контракт, а не копировать знания исходного навыка.

### Unresolved integration

Если роль отсутствует или несовместима, Installer должен оставить её `unresolved` и не объявлять систему operational.

Рекомендуемый запрос:

```text
Используй development-orchestrator-installer в режиме repair.
Повторно проверь capability mapping обязательных навыков. Для несовместимых
навыков предложи минимальные adapters. Не переписывай исходные skills.
```

## 9. Правила ведения memory.md

`memory.md` — это долговременная операционная память агента, а не документация проекта.

Подходящие записи:

- неочевидные рабочие команды;
- стабильные особенности локального окружения;
- подтверждённые ловушки проекта;
- особенности инструментов;
- внутренние операционные договорённости;
- причины решений, которые не подходят для официальной документации.

Не следует записывать:

- секреты;
- персональные данные;
- полный журнал задач;
- неподтверждённые предположения;
- сведения, которые должны находиться в README, ADR, API docs или issue tracker;
- временный прогресс текущей задачи.

При конфликте источников используйте приоритет:

```text
код и конфигурация
→ официальная документация
→ task-файлы
→ memory.md
```

`memory.md` необходимо периодически очищать от устаревших записей.

## 10. Upgrade, Repair и Rollback

### Upgrade

Используйте после обновления канонического навыка или процесса:

```text
Используй development-orchestrator-installer в режиме upgrade.
Сохрани ручные настройки, generated sections и project-specific adapters.
Покажи diff, создай backup, обнови core, затем выполни validation и dry run.
```

### Repair

Используйте после изменения конфигурации, структуры проекта или обнаружения ошибки:

```text
Используй development-orchestrator-installer в режиме repair.
Сравни manifest с фактическими файлами, восстанови только отсутствующие
или неконсистентные managed components. Не удаляй неизвестные файлы.
```

### Rollback

Rollback должен использовать installation manifest и session backup.

```text
Выполни rollback последней установки development-orchestrator.
Сначала покажи список файлов, которые будут восстановлены или удалены.
Не трогай файлы, изменённые пользователем после установки, без diff и предупреждения.
```

## 11. Типовые проблемы

| Проблема | Правильное действие |
|---|---|
| Не найден `task-manager` | Оставить mapping `unresolved`, создать contract/scaffold только с разрешения пользователя |
| Существующий code-review меняет статус задачи | Создать adapter, запрещающий lifecycle side effects |
| Платформа не поддерживает субагентов | Оставить full-cycle `blocked`; настроить платформенный launcher или выбрать поддерживаемую среду |
| Health check найден, но его безопасность неясна | Оставить `unresolved` или `manual-only`, не запускать автоматически |
| Required project tool завершился ошибкой | Остановить переход на соответствующей стадии и записать evidence в задачу |
| Команда тестов неизвестна | Зафиксировать `unresolved`, не выдумывать команду |
| Проект не имеет UI | Указать UI tests как `not_applicable` с подтверждением project profile |
| Coverage ниже порога | Исправить тесты/код либо заблокировать и запросить решение; не понижать автоматически |
| Второй review снова failed | Остановить задачу в `in_progress/blocked` |
| Пользователь не дал явный approve | Оставить `review/waiting_approval` |
| Тесты потребовали существенного изменения production-кода | Повторно выполнить доступный code-review; при исчерпанном лимите заблокировать |
| Документация не требуется | `not_applicable` с конкретным обоснованием |
| Task tracker внешний | Использовать интеграцию/adapter, не создавать параллельный backlog |
| Процесс проекта отличается от 1.1.0 | Создать Process Change Proposal и новую версию процесса |

## 12. Рекомендуемое владение системой

Для командного проекта рекомендуется назначить владельца процесса, который отвечает за:

- canonical orchestrator;
- Installer asset;
- lifecycle version;
- task schema;
- обязательные quality gates;
- adapters;
- обновление руководства;
- одобрение Process Change Proposal.

Проектная команда может менять команды, пути и integration mapping через config, но изменение lifecycle должно проходить отдельное review и approval.

## 13. Краткий рабочий сценарий

### Первичная установка

```text
1. Installer audit
2. Проверка отчёта
3. Installer install
4. Validation и dry run
5. Проверка operational status
```

### Выполнение задачи

```text
1. Создать задачу со статусом created
2. Запустить development-orchestrator
3. Оркестратор выполняет project tools и запускает два независимых review-субагента
4. Проверить отчёт в статусе review
5. Дать approve либо запросить изменения
6. Оркестратор создаёт и запускает тесты и post-test tools
7. Оркестратор обновляет документацию и memory
8. Задача получает done и переносится в completed archive
```

### Изменение настроек

```text
1. Изменить orchestrator.config.yaml
2. Запустить Installer repair
3. Проверить validation и dry run
```

### Изменение процесса

```text
1. Создать Process Change Proposal
2. Выпустить новую версию процесса
3. Обновить Orchestrator и Installer вместе
4. Определить миграцию активных задач
5. Выполнить Installer audit
6. Выполнить Installer upgrade
7. Проверить dry run и rollback
```

## 14. Главное правило

Используйте конфигурацию для настройки **параметров проекта**, adapters — для настройки **интерфейсов существующих навыков**, а новую версию Orchestrator и Installer — для изменения **самого процесса разработки**.
## Актуальные уточнения жизненного цикла

- По умолчанию тестовый gate выполняется сразу после реализации и до review. Запрос «остановиться до тестирования» является явным исключением конкретной задачи и соответствует `test_gate: after_approval`.
- Состояния review независимы. Если `task-review` завершён успешно, а `code-review` завершён с ошибкой, повторяется только `code-review`.
- Каждый повторный review получает новый изолированный контекст и нового subagent. Завершённый контекст повторно не используется.
- `create-test`, `doc-sync` и `task-manager` могут выполняться в контексте orchestrator или через обычную делегацию. Изолированные subagent обязательны только для `task-review` и `code-review`.
- При `quality.coverage_policy: configured_only` coverage проверяется только при наличии исполнимой команды, scope и threshold в `commands.coverage`. Иначе записывается `not_configured` с причиной.
- После установки должен проходить `sync_tasks.py --check`; команда выявляет устаревшие индексы.
- До реализации зафиксируйте исходное состояние Git и task-owned scope; несвязанные изменения dirty worktree не должны попадать в findings review.
